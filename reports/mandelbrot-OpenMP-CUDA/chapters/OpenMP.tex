\section{OpenMP}
\label{sec:OpenMP}

\subsection{Parallel For}
In the first approach (\texttt{src/omp1.cpp}), the outer loop over was parallelized by the directive using default static scheduling (\texttt{schedule(static)}). Evenly divides pixels among available threads.

\begin{lstlisting}
    #pragma omp parallel for
    for (int pos = 0; pos < HEIGHT * WIDTH; pos++)
    {
        image[pos] = 0;

        const int row = pos / WIDTH;
        const int col = pos % WIDTH;

        double cRe = col * STEP + MIN_X;
        double cIm = row * STEP + MIN_Y;

        // z = z^2 + c
        double zRe = 0, zIm = 0;
        for (int i = 1; i <= ITERATIONS; i++)
        {
            double oldRe = zRe;
            zRe = (zRe*zRe - zIm*zIm) + cRe;
            zIm = 2*oldRe*zIm + cIm;

            // If it is convergent
            if(zRe*zRe + zIm*zIm >= 4)
            {
                image[pos] = i;
                break;
            }
        }
    }
\end{lstlisting}

\subsection{Guided Scheduling}
The following scheduling policy dynamically balances workload distribution. It is essential for handling the computational irregularity of the Mandelbrot set algorithm because different pixels requires different amount of iterations.

\begin{lstlisting}
    #pragma omp parallel schedule(guided)
    for (int pos = 0; pos < HEIGHT * WIDTH; pos++)
    {
        // ... same content ...
    }
\end{lstlisting}

\subsection{Guided + SIMD}
Maximum optimization combining multi-thread parallelism with SIMD vectorization.

\begin{lstlisting}
    #pragma omp parallel for simd schedule(guided)
    for (int pos = 0; pos < HEIGHT * WIDTH; pos++)
    {
        // ... same content ...
    }
\end{lstlisting}









\noindent
Here, each thread computes a subset of the output frequencies independently. The temporary variables \texttt{Xr\_temp} and \texttt{Xi\_temp} are private to each thread, ensuring there is no race condition when updating the output arrays.

\subsection{Parallelization over the inner loop with reduction}

In the second approach, the inner loop over the time index $n$ is parallelized using a reduction clause:

\begin{lstlisting}
for (k = 0; k < N; k++) {
    double Xr_temp = 0.0;
    double Xi_temp = 0.0;
#pragma omp parallel for reduction(+:Xr_temp, Xi_temp)
    for (n = 0; n < N; n++) {
        Xr_temp += xr[n] * cos(n * k * PI2 / N) + idft * xi[n] * sin(n * k * PI2 / N);
        Xi_temp += -idft * xr[n] * sin(n * k * PI2 / N) + xi[n] * cos(n * k * PI2 / N);
    }
    Xr_o[k] = Xr_temp;
    Xi_o[k] = Xi_temp;
}
\end{lstlisting}

\noindent
Here, the computation of each output frequency $X[k]$ is parallelized across the time samples $n$. The \texttt{reduction} clause ensures that each thread accumulates contributions to \texttt{Xr\_temp} and \texttt{Xi\_temp} safely, avoiding race conditions. This method can provide higher parallel efficiency for large $N$, but incurs some overhead from the reduction operation, as shown in the following figures.

\paragraph{Precomputation of Trigonometric Functions:}
in an additional attempt to optimize the DFT computation, I modified the code as in the source \texttt{src/omp3.c}. The idea was to reduce the repeated evaluation of trigonometric functions by computing the sine and cosine values once per iteration:

\begin{lstlisting}
#pragma omp parallel for private(n)
for (k=0; k<N; k++) {
    double Xr_temp = 0.0;
    double Xi_temp = 0.0;

#pragma omp simd reduction(+:Xr_temp, Xi_temp)
    for (n=0; n<N; n++) {
        double angle = n * k * PI2 / N;
        double c = cos(angle);
        double s = sin(angle);

        Xr_temp += xr[n]*c + idft*xi[n]*s;
        Xi_temp += -idft*xr[n]*s + xi[n]*c;
    }

    Xr_o[k] = Xr_temp;
    Xi_o[k] = Xi_temp;
}
\end{lstlisting}

\noindent
The motivation behind this modification was that, theoretically, computing the trigonometric functions only once per iteration should reduce the overall workload and improve performance.\\

\noindent
However, the experiments did not yield significant improvements. Performance remained the same, or in some cases slightly worse. This is likely due to the compiler automatically applying this optimization by default.
